# 播放页悬浮控件（顶栏 / 控制条 / 字幕带 / 全屏 / 加载动画）

本轮把播放页中列从「视频 + 一条进度条」改成了 B 站那样的「悬浮控件」，并且让 CC 字幕
跟着控件显隐上下移动、播放取流时播官方风格的加载动画。参考系统播放器：

- B 站 App 播放页截图（用户提供 3 张：暂停态的中央播放键、播放态的顶栏快进条与底栏进度条）；
- [`zuorn/bilibili-client`](https://github.com/zuorn/bilibili-client)：Tauri 桌面客户端，
  它的 `player-header` / `player-controls` 都是「默认隐藏、`.visible` 才显示」的浮层，
  由 `playback.js` 在鼠标静止后收起 —— 交互语义与本轮实现一致。
- 参考系统播放器：顶栏结构（返回 + 标题 / 六档跳转 / 底部播放键 + 当前时间 + 进度条 +
  总时长）与 3.5s 自动收起节拍；详情页内嵌播放器的「全屏」动作是把周围的 UI
  让出去，§5 的全屏按这个语义实现。

## 1. 设备约束：为什么控件只能"占位"不能"浮层"

X6/X7 Pro 的视频走 KMS overlay 平面，`zpos` 高于 Falcon UI（`docs/x6pro-video-playback.md`
§3.1 真机 `Esmart1-win0 zpos 2` vs `Esmart0-win0 zpos 0`），**UI 像素压不到画面上**；
项目又不用 `position:absolute` / `z-index`（falcon 上不可靠）。所以：

- B 站那种「控制条半透明浮在视频上」在这里做不到；
- 唯一可靠的做法是**让出真实 UI 像素**：中列高度被切成四段，四段之和恒等于视口高：

```
中列高 = 视频洞 video + (字幕带 cc) + 控制条 bar      （第十四轮起，顶栏 top 恒 0）
X7 Pro（280）默认（无字幕）：     248 +  0 + 32 = 280  → 16:9 画面 441x248
X7 Pro（280）开着字幕：           230 + 18 + 32 = 280  → 16:9 画面 409x230
X7 Pro（280）全屏：               与上面两行**完全相同**（只是 x 居中）
X6 Pro（266）默认 / 有字幕：      216 + 0 + 30 / 198 + 18 + 30 = 266
直播态：                          280 +  0 +  0 = 280
```

⚠️ **几何只在两种操作下变**：进/出全屏（只改 x，不改尺寸，见 §13）和开关字幕
（18px 让进让出）。控件显隐**不**改几何 —— 控制条那一段恒定占位，隐藏只是把内容
换成纯黑。第七~九轮那种「收起控件 → top/bar 归零 → 视频洞吃掉两段」的动态分段在
X7 上会毁画面，原因见 §9.1；`planBands()` 仍保留完整四段能力供单测/其它机型使用。

**第十四轮把顶栏删了**：那 18px 直接还给画面，默认状态下 16:9 从 409x230 变
441x248（面积 +16%）。顶栏原来的四件事都有新去处：标题在左列、暂停标记由控制条
的播放键承载、±10s 进控制条、返回键只在全屏态出现在控制条最左。

控制条 32（X6 上 30）这个数字是 3.5.6 第九轮从 27/26 抬上来的：真机反馈「暂停按钮
太小」，27 高的条里塞不下能戳中的圆键。代价是画面少 4~5px 高（16:9 上是 7~9px 宽），
肉眼看不出来。`layout.js` 的 `seekH` 与 `play_chrome` 的 `barH` 仍是同一个来源。

- 段高由 `src/services/play_chrome.js::planBands()` 算，页面摆 DOM、`play_session.js`
  算 `render-rectangle` 都用同一份数字（`bandBox()`），两边不同源就会重演 3.5.6 的
  「画面与点击热区错位」；
- 运行时切换控件/字幕/全屏不重取流，只 `player.setVideoRect()` 热更新 kmssink 的矩形。
  取流中（`loading`）改的会落在 `_rectDirty` 上，起播后由轮询的 `playing` 分支补一次 ——
  否则会出现「进全屏时还在转圈 → 起播后画面仍卡在 457 宽的中列」的半截态。

## 2. 交互

| 操作 | 行为 |
| --- | --- |
| 单击视频空白处 | 收起整套控件：顶栏 + 控制条归零，视频洞吃掉这两段，**字幕带留在最底部**（控制条原来的位置） |
| 再点一次 | 控件展开：画面缩小让位，**字幕带上移**夹到画面与控制条之间 |
| 暂停 | 强制展开控件：顶栏居中显示「⏸ 已暂停」胶囊，控制条左侧播放键变成 ▶ |
| 暂停时点画面 | 继续播放（B 站习惯，暂停标记不会因为误触消失） |
| 控制条左侧按钮 | 暂停 / 继续 |
| 顶栏 `←` | 普通态 = 离开播放页；**全屏态 = 退出全屏**（全屏时没有左列返回键，这个键若还画箭头，一点就把整段视频关掉） |
| 顶栏 `-1m` / `-10s` / `+10s` / `+1m` | 相对定位，落点钳在 `[0, duration-1000ms]`；分钟档是照参考系统播放器的 `jump-buttons` 加的（笔尖在 457px 的轨道上本来就拖不准） |
| 控制条轨道 | 拖动定位（拖动中零请求，松手后 250ms 下发一次） |
| 控制条「字幕」 | CC 开关（有轨道/已开启时才出现） |
| 控制条「全屏 / 退出」 | 进 / 出全屏（§5）；直播态没有这条控制条，也就没有全屏入口 |
| 全屏态静默 3.5s | 控件自动收起（`AUTO_HIDE_MS` + `canAutoHide()`），**只在这一种情形下**自动收 |
| 互动题面出现 | **强制退出全屏**：题面画在右列，全屏时右列让位，不退会出现「片子停在片尾、屏幕上一个能点的东西都没有」 |
| 直播 | 没有控件也没有字幕带（无时长、seek 无意义），点画面仍是暂停/继续 |

> 暂停标记为什么不是画面正中的大图标：KMS 平面盖在 UI 之上，中间那块像素画不上去。
> 因此标记做成**画面正上方居中的胶囊**（这条带子是真正的 UI 像素），配合控制条里
> 高亮的播放键。等哪天真机能证明 UI 平面在最上层（`kmsProbe()` 里比 zpos 即可），
> 再把 `chrome-top` 改成 `position:absolute` 的浮层即可，几何部分不用动。

## 3. 几何与命中测试

- `barMetrics(midW, {cc, fs})` 给出控制条各槽位宽度（播放键 30 / 时间 44 / 字幕 32 /
  全屏 32 / 间距 4 / 左右 padding **0**），**轨道宽 = 中列宽 − 其它槽位**，DOM 的 `width`
  与 `seekRatioAt()` 的命中测试用同一个数字（旧实现把 453 写死在页面里，布局一改就静默错位）；
- **padding 必须是 0**：`.chrome-bar` 原来有左右各 8px 的 CSS padding，`barMetrics` 又扣
  了一遍 `BAR_PAD_X*2`。若 falcon 的 `width` 含 padding（border-box），最后那个槽位
  （全屏键）就被挤出可视区 —— 真机反馈的「没有全屏按钮」正是这么来的。pad 归零后
  「子元素之和 === 中列宽」在两种盒模型下都成立，单测守着这条守恒；
- `.cb-btn` 不描边：`border-width: 1px` 在 content-box 下会让每个按钮实宽 +2，
  四个带边框的控件足以撑爆控制条。要区分就用底色，不用边框；
- 触点绑定在 `.cb-hit`（**撑满 32/30 高**的命中区，视觉轨道只有 10px）上，
  falcon 的 `pageX` 是相对绑定元素的坐标，所以 `trackRatioFromX(x, trackW)` **不再减 padding**；
- 站内已无 `.seek` / `.seek-track` 这两个类名，`.seek-fill` / `.seek-knob` 继续复用；
- 全屏态中列宽从 457 变成 936，轨道宽自动跟着变 —— 这是把 `midW` 做成 computed、
  所有带子和 `barMetrics` 都从它取值的原因（否则会出现「视频满了、控件还是 457 宽」）。

## 4. 加载动画

取流期间 `play.state === 'loading'`，此时 `holeVisible` 为 false，整块视频区都是 UI 像素，
正好用来播动画：

- 小电视（2px 粉色描边 + 深色屏幕）里一条 10px 宽的蓝色扫描条左右乒乓；
- 下面三个 5px 圆点轮流高亮（每个 240ms）；
- 文案「正在加载视频…」。

falcon 上没有可靠的 `@keyframes` / `transform`，所以动画由 `ui.frame` 在 120ms 的
`setInterval` 里推进，`loadingFrame(tick)` 把帧号映射成 `{dot, dx}`。
定时器只在 `state === 'loading'` 时运行：起播成功、报错、`teardown` 都会
`stopLoadingAnim()`（`tick` 里还有一道兜底，看门狗把状态改成 error 时也会停）。

## 5. 全屏（3.5.6 第七轮）

参考系统播放器详情页内嵌播放器的「全屏」动作：**把周围的 UI 让出去**，不换管线。
本项目落地为 `ui.full` 一个布尔量：

```
普通态：left(208) + mid(457) + right(271) = 936
全屏态：视频洞独占 936，左右两列 v-if 掉，顶栏/控制条自动收起
```

- `playFull` 还要求 `!isLivePlay`：直播没有控制条（无时长、seek 无意义），
  也就没有全屏按钮的落点，硬塞入口会和「点画面 = 暂停/继续」打架；
- 进/出全屏只下发一次 `player.setVideoRect()`，不重取流、不断播；
- 按钮在控制条最右（`cb-fs`，30px 宽），全屏态文字变「退出」并染成品牌粉；
- 顶栏左侧在全屏态变「退出」两个字 —— 那时候没有左列返回键，若还画返回箭头，
  用户一点就会把整段视频关掉；
- 进出全屏后 `barMetrics` 的轨道宽、`bandBox` 的信箱盒子都跟着 `midW` 走，同源。

### 5.1 为什么全屏态要把字幕挪到顶栏

这是一笔必须算清楚的账。视口 936×280 是 **3.34:1**，16:9 内容在这么宽的屏上
**永远是高度受限**（fit 后 498×280 就已经贴满上下沿）：

| 情形 | 视频洞 | 16:9 画面 | 相对普通态 |
| --- | --- | --- | --- |
| 普通态（控件收起，留 28px 字幕带） | 457×252 | 448×252 | — |
| 全屏态 + 留 28px 底部字幕带 | 936×252 | **448×252** | **完全没变** |
| 全屏态 + 无字幕带 | 936×280 | 498×280 | 面积 +23%（线性 +11%） |
| 全屏态 + 字幕借顶栏 18px | 936×262 | 466×262 | 面积 +8% |

所以「全屏 + 底部字幕带」在 16:9 稿件上是**一点都不会变大的** —— 用户会觉得
按了没反应。因此全屏态把字幕改由顶栏那条 18px 承载（`planBands` 的 `ccInTop`）：

- 控件收起时那条带子画字幕（`.chrome-cc` + `.cc-text-top`，只能单行 11px）；
- 控件展开时它变回标题 + 跳转键，字幕暂不上屏（3.5s 后控件自收，字幕回来）；
- 顶栏被挤成 0（视口极小时）`ccInTop` 跟着失效，宁可没字幕也不让四段加起来超视口；
- 想再大一点就在控制条关掉「字幕」→ 498×280。

副作用要说清楚：**全屏态字幕在画面上方**。这是设备约束逼出来的（字幕只能落在
UI 像素里，全屏态唯一的 UI 像素就是顶栏那条带），不是设计偏好。

### 5.2 自动收起

`AUTO_HIDE_MS = 3500`，由 `canAutoHide(state, {full, chrome, busy})` 判定：
只在「全屏 + 控件展开 + 真的在播 + 没在拖进度条/没有互动题面」时计时；
暂停、播完、出错、取流中一律不自动收。

**普通态不自动收**：那里的画面由 457 宽的中列决定，控件一收画面会自己变大，
用户没点任何东西却看到布局跳变，很容易当成 bug —— 普通态仍然只认「点画面」。

### 5.3 两个会卡死的边角

- **互动题面**画在右列，全屏时右列让位 → 题面出现前必须 `exitFullForInteract()`，
  否则 `pause_video=1` 的片段会在片尾停住、屏幕上没有任何可点的东西；
- **取流中切全屏**：`applyVideoGeometry()` 会因为「还没出画面」直接返回，
  这时置 `_rectDirty`，起播后补一次矩形。

## 7. 第九轮：真机六条反馈的根因与修法

用户拿参考系统播放器的三张照片逐条对比，报了六个问题。逐条记下来，
因为其中**四个是同一个根因**，不写清楚下次还会以为是四个独立 bug。

| 反馈 | 根因 | 修法 |
| --- | --- | --- |
| 进度条卡在开头 | `tick` 里 TDZ 抛错（见下） | 把 `seekWaiting` 的声明提到第一个使用点之前 |
| 字幕无法显示 | 同上（`_ccAnchor` 永不更新 → 永远取 `pos=0` 那句） | 同上 + 有轨道且用户没选过时自动打开 CC |
| 互动播完没有选项 | 同上（末尾判据 / `handleSegmentEnd()` 整段不执行） | 同上 |
| 没有全屏按钮 | 控制条宽度被算两遍（CSS padding + `BAR_PAD_X`），末位槽位被挤出可视区 | `BAR_PAD_X = 0`、CSS 去 padding、`.cb-btn` 去描边 |
| 暂停按钮太小 | `.cb-play` 24×22、图标 16；条高只有 27 | 条高 30/32、圆键 30、图标 20，暂停态实心品牌粉 |
| 点两下屏幕视频跑到下方 | ① `.pvideo` 与 `<hole>` 都绑 click，一次点击 toggle 两次；② 两次 `setRect` 背靠背，`render-rectangle` 是 write-only 属性，可能停在中间态 | 300ms 连点闸 + 「矩形没变就不下发」+ native 改走 `GstVideoOverlay`（见 §8） |
| 进度条是"挖洞"不是"透明" | 三条带的底色是 `#0D1015` / `#101318`，和视频黑差一档，边界一眼可见 | **三条带**统一 `#000000`（中列本身仍透明，理由见 `base.less` 的 `.pmid` 注释），无边框无圆角容器；轨道 10px、填充 10px、圆点 16px |

### 7.1 TDZ：一个作用域事故让四个功能一起哑火

`tick` 里在**函数开头**读了 `seekWaiting`（决定要不要更新字幕锚点），而它是函数
**末尾**才 `let` 声明的。同一函数作用域里 `let/const` 有 TDZ，于是每一轮 tick 都在
那一行抛 `ReferenceError: Cannot access 'seekWaiting' before initialization`。

后半段（位置回写 `play.positionMs`、`isStreamEnded` 末尾判据、`handleSegmentEnd()`、
`st.state` 跟随）全都不执行。表现出来就是三个互不相干的症状：进度条不动、字幕不出、
互动播完没选项 —— 而日志里只有一行没人看的未处理拒绝。

两条防线：

1. 声明挪到第一个使用点之前（唯一声明点）；
2. `setInterval(() => tick().then(null, err => logWarn('poll tick 异常…')))` ——
   任何抛错都要打点，并且下一轮照常跑。`test/run.js` 里有一条静态断言守着「声明在
   使用之前」和「兜底存在」，不用真机就能回归。

### 7.2 为什么「点两下」会把画面弄到下方

`render-rectangle` 是 **write-only** 属性，kmssink 只在重新 configure（分配 plane）
那一刻读它。两次 `setRect` 背靠背到达时，第二次可能写在一个"正在 configure"的属性上，
平面就停在一个既不是 A 也不是 B 的中间态。用户看到的是画面被推到下方/只露半截。

三层处理：

- **连点闸**：`onVideoTap` 300ms 内只认第一次（`.pvideo` 与 `<hole>` 都绑了 click，
  一次物理点击有可能两个都收到）；
- **去重**：`applyVideoGeometry` 记住上一次**成功下发**的物理矩形，相同就不下发。
  点两下 = 收起又展开 = 几何回到原样 → native 一次都不碰；
- **换 API**：见 §8。

## 8. native：运行时改矩形改走 GstVideoOverlay

`PB2_CMD_SET_RECT` 原来写 `render-rectangle` 属性，于是「放大」在运行期不可靠，
1x1 之后更是必须靠一次 seek 重建管线才能回来（见 `session.c` 里的棘轮注释）。

参考系统播放器用的是 `gst_video_overlay_set_render_rectangle()`：这条路直接调用 sink
的实现，kmssink 自己重配 plane，**放大缩小都生效、不需要重建管线**。

现在 `session.c` 里：

- `pb2_overlay_fn()`：`dlopen` + `dlsym`，只探一次，结果缓存；拿不到就打一行
  `overlay api: unavailable (fallback: render-rectangle property)`；
- `overlay_apply_rect()`：把已经偶数对齐的 `g_w.rect` 交给它；
- `SET_RECT` 的「正常尺寸之间」分支优先走 overlay，失败才回落到老的
  「写属性 + 暂停态脉冲 200ms」—— 老设备行为逐字节不变。

`libs/libjsapi_player2.so` 因此多了一条 `NEEDED libdl.so.2`（构建脚本的链接行加了
`-ldl`）。真机日志里搜 `overlay api:` 就能确认这台设备是否走了新路径。

## 9. 第十轮：X7 上「运行时改矩形」是错的，几何必须恒定

三张真机照片（`IMG_20261109_012712` / `012716` / `012719` / `012729`）：

- 刚进视频：画面居中、控制条六个槽位都在、时间 00:02 / 02:29，**正常**；
- 点一下隐藏控件：顶栏和控制条确实消失，但画面变宽、被推到下半屏、底部几乎贴边；
- 关掉字幕后，控制条里的「字幕」按钮**整个消失**，控制条只剩「全屏」。

### 9.1 画面跑偏：不是 setRect 写得不对，是 caps 定死了

`session.c::video_post_rate_desc()` 在 `sw_scale=1`（X7 默认）时往管线里插：

```
videoscale ! video/x-raw,width=<g_w.rect.w>,height=<g_w.rect.h>
```

caps 是 **OPEN 那一刻**按起播矩形算好的，之后不再协商。播放中改
`render-rectangle`，kmssink 拿到旧尺寸 buffer 却要往新矩形里贴 —— 画面被拉伸、
位置错乱。源码里那句「X7 自选平面疑似只做 1:1 贴 buffer，改 render-rectangle
对显示尺寸毫无作用」说的是同一件事的另一半。

所以第九轮加的 `GstVideoOverlay` 不是解药：它让"改矩形"**真的生效了**，反而把
破坏做得更彻底。参考系统播放器能用 setRect，是因为它根本没插 videoscale
（`force-aspect-ratio=true` 交给 kmssink）。

**结论：起播后不许改矩形。** 现在：

| 段 | 普通态 | 全屏态 |
| --- | --- | --- |
| 顶栏 top | 18（恒） | 18（恒） |
| 视频洞 video | 230 | 262 |
| 控制条 bar | 32（恒） | 0（恒） |
| 字幕带 cc | **0（取消）** | 0 |

- 控件隐藏 = 顶栏/控制条**内容换成纯黑**，那两段像素照样占着，DOM 与 native
  矩形一像素都不变；
- 字幕改由顶栏 18px 单行承载（参考系统播放器的字幕也在画面上方），不再有独立
  28px 字幕带 —— 开关字幕只是换一行文字；
- `applyVideoGeometry()` 只放行 `full-*` 的下发，其它原因一律打日志跳过；
- native 的 `SET_RECT` 在 `sw_scale` 档也做了防御：只更新 `g_w.rect` 并投递
  一次原地 seek，让 `build_pipeline` 用新矩形重算 caps 后重建平面，**绝不即时
  动 plane**。全屏切换因此会有一次约 500ms 的重建，这是 X7 上唯一可靠的换尺寸途径。

### 9.2 字幕按钮消失

`ccBtnVisible` 原来是 `tracks.length > 0 || cc.on || cues.length > 0`。稿件没有
CC 轨道时，用户点一下开、再点一下关，三个条件同时落空 → 按钮从控制条里消失，
再也没有入口打开。现在**点播态恒可见**，槽位数固定，轨道宽度也不再随开关抖动。

### 9.3 diag 自检页补齐取证能力

用户反馈「diag 界面没有进度条，无法查找 bug」。现在：

- 面板里加了一条真实进度条 + 状态行（`state / 位置 / 时长 / 帧数`），每秒读
  `player.status()`，不用 adb 就能看到进度是否在推进；
- 日志页顶部加「关键 / 全部」切换，关键视图只留
  `SET_RECT | OPEN rect | overlay api | videoscale | [chrome] | [cc] | poll tick |
  video ended | deferred` 等能判案的行，避免 amixer 噪音把现场刷出窗口。

## 10. 第十一轮：字幕「根本无法显示」的答案是登录态，不是渲染

真机反馈只有一句：「字幕没有起作用，根本无法显示」。这一轮没有改渲染，
因为拿真接口验证下来，**字幕数据在到达渲染之前就已经是空的了**。

### 10.1 实测证据

同一个稿件（BV1GJ411x7h7 / cid 137649199），匿名请求两个接口：

```
① GET x/player/v2?bvid=..&cid=..
   data.subtitle.subtitles = []                      ← 一条轨道都没有

② GET x/web-interface/view?bvid=..
   data.subtitle.list = 12 条轨道（zh-CN / zh-Hans / ja / en-US …）
   但每一条 subtitle_url 都是空串
```

也就是说：稿件**有** 12 条字幕轨，B 站只是不给匿名用户字幕文件的地址
（`subtitle_url` 里带 `auth_key`，必须 SESSDATA）。`player/v2` 是字幕的唯一入口，
它返回空数组，后面 `pickSubtitleTrack → fetchSubtitleCues → cueAt` 全都是空转。

用户那台设备右下角写着「未登录 · 不能评论」，与这个结论一致。

### 10.2 改法：原因放「我的 → CC 字幕」，播放器只留「字幕」

按用户要求，**播放器里不再解释字幕状态**（顶栏那 18px 恢复成标题/暂停标记，
控制条只保留「字幕」这个开关）。原因统一写在「我的 → CC 字幕」下面那行
（`ccSettingHint`）：

| 状态 | 设置页文案 |
| --- | --- |
| 未登录 | 未登录：B 站匿名接口不返回字幕地址，登录后才能显示字幕。点上方「扫码登录 B 站账号」即可。 |
| 正在拉字幕 | 字幕加载中… |
| 已加载 | 已加载 N 句字幕（中文（简体））。 |
| 有轨道但下载/解析失败 | 已找到 N 条字幕轨，但内容没取到：具体原因。 |
| 已登录但该稿没有 CC | 该稿件暂无 CC 字幕。换一个带 CC 字幕的视频试试。 |

- 自动打开失败**不再把开关回退成关**（以前会，等于把唯一的线索也关掉了），
  保持开启，让设置页那行有内容可写；
- 扫码登录成功后，如果还在播放页会补拉一次字幕（`onLoginSuccess` 末尾）；
- 日志新增一行判案：`[cc] player/v2 tracks=N login=0/1 ccOn=0/1`，
  成功时再打 `[cc] loaded N cues lang=.. first=起-止ms 文本前 12 字`。
  diag 的「关键」视图已经把 `[cc]` 收进过滤正则。

### 10.3 这不是代码能绕过去的

试过的匿名路径全部无效：`x/player/v2`（含 WBI 版）、带真实 `buvid3/4`
（`x/frontend/finger/spi` 现取）、`x/player/playurl`、App 端 `x/v2/view`、
以及网页 HTML 内嵌状态。匿名一律拿不到 `subtitle_url`。

所以字幕的正确前提是：**在「我的」里扫码登录**。登录后同一个稿件会返回
`subtitles[]`，`subtitle_url` 带 `auth_key`，`fetchSubtitleCues` 直接下载解析，
不需要任何额外开关。

## 11. 第十三轮：全屏压扁 / 全屏没有进度条 / 返回键太小

真机（全屏截图）：画面被压扁且偏到右下、底部没有进度条；顶栏的「退出」
只有 24×18 的裸文字。

### 11.1 全屏压扁：因为全屏改了视频矩形的**尺寸**

第十轮起全屏是 `top=18 + video=262 + bar=0`，普通态是 `18+230+32`。进全屏
把视频段从 230 拉到 262，`videoscale` 的输出 caps 从 409x230 变成 466x262；
X7 在 `SET_RECT` 后要靠一次原地 seek 重建管线才能让 caps 跟上，重建窗口里
kmssink 仍可能拿旧 buffer 贴新矩形 —— 真机就是压扁 + 偏移。

**改法：全屏不再改视频尺寸，只改位置。**

| 段 | 普通态 | 全屏态 |
| --- | --- | --- |
| 顶栏 top | 18 | 18（保留「退出」） |
| 视频 video | 230 | **230（不变）** |
| 控制条 bar | 32 | **32（保留）** |

16:9 的矩形在两种状态下都是 409x230，只有 x 从 232 变成居中 263 ——
caps 不需要重算，即使重建没完成也不会变形。代价是全屏不会把画面放大：
X7 的 `videoscale` caps 在起播时定死，换尺寸必然重建，重建就会变形，
这是硬限制。

### 11.2 全屏没有进度条：bar 归零后没有 UI 像素可画

原来的全屏 `barH=0`，控制条整段让给画面。KMS 平面盖在 UI 之上，进度条
画不到画面上，所以「全屏后点下方」什么都不会出现 —— 不是点击没生效，
是**根本没有那条 UI**。

现在全屏保留 32px 控制条；控件收起时它是一条纯黑占位，`onBarTap()` 绑在
`.chrome-top` / `.chrome-bar` 上，点这两条任意位置都能把控件叫回来
（以前只有 `.pvideo` 绑了 `onVideoTap`，点黑条没反应）。

### 11.3 返回键

`.ct-back` 24×18 / 9px → **46×18 胶囊 / 11px 白字**，底色品牌粉 28%
（顶栏只有 18px 高，不能再高；要的是横向命中面积）。

## 12. 第十四轮：删顶栏把画面放大 16%，并修掉「糊」

真机反馈三句话：

1. 「把进度条背景改为透明的，像 media 那样」；
2. 「把视频放大，占满视频区，本身就没有多大的地方，进度条还占些」；
3. 「视频播放有一些糊，就算是 360p 的也不应该这么糊」。

### 12.1 「透明」在这台设备上做不到，但「看不出挖洞」可以

`video/x-raw` 走的是 KMS overlay 平面，zpos 高于 Falcon UI —— UI 画不到画面上，
这是从 3.5.5 起就没变过的硬约束（§0 文件头的结论）。参考系统播放器能
"浮"在画面上，是因为它用 `GstVideoOverlay` 把视频交给自己的窗口系统合成，
UI 和视频在同一块 framebuffer 里；我们的 UI 在另一个平面。

所以这一轮没有去追"真透明"，而是把**占位本身做到几乎看不见**：

- 顶栏整段删除（18px 还给画面）；
- 控制条上下都没有边框/圆角/亮一档的底色（第九轮已统一 `#000000`）；
- 中列（`.pmid`）与视频信箱黑同色 —— 整列看起来就是一块黑屏，进度条"长"在上面。

三层叠加的结果：默认状态下画面 441x248 居中在黑列里，下面一条 32px 黑带只放
一条进度条和几个钮。视觉上和"叠在画面上"已经没什么区别。

### 12.2 画面放大的账（X7 936x280、中列 457）

| 版本 | 分段 | 16:9 画面 | 面积 |
| --- | --- | --- | --- |
| 第十轮 | 顶栏 18 + 视频 230 + 控制条 32 | 409x230 | 94 070 |
| **第十四轮（无字幕）** | 视频 248 + 控制条 32 | **441x248** | **109 368（+16%）** |
| 第十四轮（开字幕） | 视频 230 + 字幕 18 + 控制条 32 | 409x230 | 94 070 |

顶栏原来的四件事：

| 原功能 | 新位置 |
| --- | --- |
| 视频标题 | 左列顶部本来就有，不重复 |
| 暂停标记（「已暂停」胶囊） | 控制条播放键：暂停态实心品牌粉 + 白色三角 |
| -1m / -10s / +10s / +1m | 控制条里的 `-10s` / `+10s`（分钟后缀去掉，拖进度条更快） |
| 返回（仅全屏态） | 控制条最左的 `.cb-back`，30x30 |

### 12.3 字幕带回来了，但只给 18px 一行

顶栏没了，字幕不能"借顶栏"，只能回到独立带子。区别是**它现在只在真有句子时存在**：

- 默认（未登录 / 无 CC）→ `cc = 0`，视频洞 248，画面最大；
- 开字幕 → `cc = 18`，视频洞 230，画面 409x230。

这一次重建只在开/关字幕时发生（低频），换来的是默认状态下多 16% 面积 ——
而这台设备默认就是未登录（B 站匿名不给字幕 URL，见 §10），所以绝大多数时候是最大画面。

`planBands()` 为此加了 `ccFull` 选项：传 `true` 时全屏态也有自己的字幕带，于是
**全屏与普通态在同样的字幕状态下视频段高度完全相同**，进出全屏连尺寸都不用改。

### 12.4 顺手修掉两处「宽度算了两次」

| 位置 | 旧值 | 新值 | 后果 |
| --- | --- | --- | --- |
| `.cb-time` | CSS 44 | 40（= `BAR_TIME_W`） | 两格各多 4px，控制条超宽 8px |
| `.cb-btn` | CSS 32 | 30（= `BAR_CC_W` / `BAR_FS_W`） | 两个按钮各多 2px，再超 4px |

合计 12px 溢出 —— 末尾的「全屏」键就是这么被挤出可视区的（第九轮只修了 padding
那一半，没发现子元素自己也各写了一份宽度）。现在 CSS 与 `barMetrics` 逐项对齐，
单测守「子元素之和 === 中列宽」。

### 12.5 糊：`videoscale` 一直在用默认的 bilinear

`video_post_rate_desc()` 切的是：

```
videoscale ! video/x-raw,width=444,height=250
```

**没有 `method`**，于是走 GStreamer 的默认 bilinear。而这里的缩小倍率是 4.3 倍
（1920x1080 → 441x248）：bilinear 在大倍率缩小下不做抗锯齿预滤波，每 4.3 个输入
像素只取 2x2，等于抽点，细节直接丢掉 —— 真机观感就是"糊"，而且 360p 源被这样
抽一遍也救不回来。

改成 `videoscale method=lanczos`（6-tap，按缩放比例扩展 support，等效先低通再重采样）。
代价是 CPU：每输出像素约 36 次采样，441x248@30fps 约 1.2 亿次/秒。真机上如果出现
持续丢帧，把这一行改回 `videoscale`（不加 method）即可回退，日志里
`video: videoscale -> WxH method=lanczos` 能直接确认当前走的是哪条。

### 12.6 native：只移动不重建

第十三轮把全屏改成"只改位置不改尺寸"后，`SET_RECT` 在 `sw_scale` 档仍然一律投递
原地 seek 重建管线 —— 但 `videoscale` 的输出 caps 只由 width/height 决定，x/y 变化
根本不需要重协商。现在先比较 normalize 前后的 w/h：

- **尺寸变了**（开关字幕）→ 投递 seek 重建（唯一能让 caps 跟上的路）；
- **只有位置变了**（进/出全屏）→ 直接走 `GstVideoOverlay.set_render_rectangle()`，
  不重建、不黑屏。日志里是 `SET_RECT ... via overlay [move only, no rebuild]`。

### 12.7 起播就变形：caps 里没写 `pixel-aspect-ratio`

第十四轮第一次交付后，真机反馈「现在不用点，视频就扁了」。照片里画面宽高比约
**3.08:1**，而源是 16:9 —— 比值 3.08 / 1.78 = **1.73**，非常接近一次"按 16:9 的
PAR 拉伸"。

`video_post_rate_desc()` 原来只写：

```
videoscale method=lanczos ! video/x-raw,width=440,height=248,framerate=60/1
```

**没写 `pixel-aspect-ratio`。** caps 里不写，videoscale 会把源 caps 的 PAR 原样带
下来；而 kmssink 的 `force-aspect-ratio=false` 只跳过「我自己算信箱」，**不跳过
「按 PAR 拉伸」**。于是：

- 矩形尺寸完全正确（日志里 `OPEN rect` / `SET_RECT` 一切正常）；
- caps 的 width/height 也正确；
- **但 sink 认为"一个像素应该是 16/9 宽"**，横向一拉，人就成了宽脸。

这类故障最阴的地方是**所有数字都对**，只有画面不对。

修法：caps 里显式钉死方形像素：

```
videoscale method=lanczos !
  video/x-raw,width=440,height=248,framerate=60/1,pixel-aspect-ratio=1/1 !
```

同时给一个免打包的对照档：`bili_device_profile = {"swScale":3}` → 插 videoscale
但**不加 method**（默认 bilinear）。如果切到 3 之后画面正常、切回 1 又变形，
那问题就在 lanczos 的协商路径而不是 PAR，两者可以一次分清。

自检页的状态行也补了取证字段：

```
播放 playing · 00:12 / 01:54 · 帧 361 · rect <0,279,248,441> sw=1
```

`rect` 是 native 里**真正生效**的 `render-rectangle`（物理坐标，已含 panelOffset），
`sw` 是当前缩放档。页面算的矩形、`OPEN` 日志里的矩形、这一格，三者一比就知道
问题在页面、在 native、还是在 caps。

## 13. 第十五轮：全屏 = 视频铺满 + 控制面板搬到右侧黑边

真机反馈两句：「点击全屏还是不行」「自检页单独包加上进度条和全屏按钮，同时显示日志」。

### 13.1 为什么"点了全屏像没点"

上一轮把全屏做成「只改 x 不改尺寸」：普通态 441x248 居中在中列（x≈216），
全屏态 441x248 居中在整个视口（x≈247）。**只挪了 31px**，肉眼几乎看不出来。

而 native 那条"只移动"的捷径是这样的：

```
sw_scale 档 + 尺寸没变 → 走 overlay_apply_rect()
                       → 拿不到 libgstvideo 就掉进"写 render-rectangle 属性"
                       → 而 X7 的 kmssink 只在 configure 那一刻读这个属性
                       → 画面纹丝不动，日志却写着 "SET_RECT ... took 3ms"
```

**"成功但无效"** —— 比报错更难查。现在收紧判据：`sw_scale` 档只要拿不到
overlay 接口，就一律走原地 seek 重建，不再赌属性生效。

### 13.2 全屏真正的形状

这块屏 3.34:1，16:9 永远高度受限。底部留 32px 控制条，画面就只能是 441x248，
和普通态一模一样 —— 那「全屏」就永远没有意义。所以：

| 状态 | 分段 | 16:9 画面 | 面积 |
| --- | --- | --- | --- |
| 普通 | 视频 248 + 控制条 32 | 441x248 | 94 070 |
| **全屏** | 视频 280 + **控制条 0** | **498x280** | **139 440（+48%）** |

控制条没有消失，它**搬到了画面右边的黑边上**：

```
┌──────────────┬───────────────────┬──────────┐
│  黑边 219px  │  视频 498x280     │ 面板 160 │
└──────────────┴───────────────────┴──────────┘
```

- `.pmid` 在全屏时加 `.pmid-row`（`flex-direction: row`），子节点变成
  「视频列（视频 + 可选字幕带） / `.fs-gap` 弹性空隙 / `.fs-panel`」；
- `.fs-panel` 里竖着排：退出 / 播放键 + 当前时间 / 进度条 / 总时长 / ±10s / 字幕；
- 面板**常驻**，没有自动收起 —— 那 160px 本来就是黑边，收起来只会让用户
  以为按钮丢了；
- 超宽片源（右侧黑边 < 120px）自动退回「底部控制条」的老布局：
  `fsSide` 为 false，`barH` 回到 `seekH`，画面不变大但控件还在。

### 13.3 进度条的宽度只有一个出口

`seekTrackW()`：全屏 = `fsPanelW - 16`，普通 = `barMetrics().track`。
`seekFillW()`、`trackStyle()`、`seekRatioAt()` 全部走它 —— 两个布局下
"点哪儿跳哪儿"必须完全一致，否则又会重演写死 453 那类静默错位。

### 13.4 自检页（diag 单包）变成一台可操作的播放器

用户要求在自检包里也能测全屏，并且**同时**看到日志。现在自检页：

- 视频洞下方挂一条 28px 控制条：`暂停/播放 | 00:12 | 轨道 | 01:54 | 全屏`，
  洞高同步扣掉 28（`(H-28)×16/9 = 448`），画面边界与洞边界仍然严格重合；
- 轨道可拖、松手下发 `player.seek()`，位置由 `status()` 每秒回读；
- **全屏键**：视频列铺满整个视口宽（洞高不变 → 一次"只移动"的 SET_RECT，
  正好验证 13.1 那条新路径），面板整块让位；
- **同屏日志**：面板底部常驻 3 行关键现场（`SET_RECT / OPEN rect / videoscale /
  overlay api / [diag]`），每 2s 刷新，可「停/跟」；
- 状态行仍然给 `rect <x,y,w,h> sw=N` —— 与同屏日志一对照，"JS 没下发"
  还是"native 没生效"立刻分开。

高度预算（280）：标题 18 + 8 步 128 + 三行信息 48 + 日志 49 + 按钮 26 = 269，
所以步骤行高从 20 收到 16、摘要改成单行 10px。

## 14. 第十六轮：控件按参考系统播放器的数值重做；全屏只留一个出口

这一轮不是"再调一版样式"，而是把参考系统播放器里**真正在用的那组数**搬过来，
替换掉我们自己攒的那套。

### 14.1 参考系统播放器的控件度量

```
top-bar        40px   linear-gradient(to bottom, rgba(0,0,0,0.8), rgba(0,0,0,0))
  top-left / icon-wrapper 30px / back-icon / video-title
  top-right / jump-buttons / jump-btn / jump-text / action-btn / action-text
bottom-bar     55px   linear-gradient(to top, rgba(0,0,0,0.8), rgba(0,0,0,0))
  play-btn / play-icon-img
  time-current 42px  #dddddd
  video-seekbar
  time-total   68px
seekbar 参数：activeColor=#FF6699  track=rgba(255,255,255,0.3)  handle=白色
```

放大真机截图量出来：轨道 ≈4px、滑块 ≈12px、播放键是**粉底圆 + 白图标**、
按钮没有底板（action-btn 是纯文字）。

我们之前的版本：轨道 10px、滑块 16px、播放键暗底只有暂停才变粉、
每个按钮都铺一层 10% 白的圆角块 —— 在黑底上就是一条明显的"凹槽"，
这正是用户说的「你这是挖洞，人家是透明的」。

### 14.2 哪些照搬，哪些必须改

| 项 | 参考系统播放器 | 本项目 | 原因 |
| --- | --- | --- | --- |
| 轨道高 | ≈4px | **4px** | 照搬 |
| 轨道色 | `rgba(255,255,255,0.3)` | **同值** | 照搬 |
| 已播放色 | `#FF6699` | **`@accent-play: #FF6699`** | 照搬（比主色 #FB7299 亮一档） |
| 滑块 | ≈12px 白 | **12px 白**（`SEEK_KNOB_W`） | 照搬 |
| 当前时间 | 42px / `#dddddd` | **42px / `#DDDDDD` / 11px** | 照搬 |
| 播放键 | 粉底圆 + 白图标 | **同**（恒粉，状态只靠图标） | 照搬 |
| 字幕/全屏键 | 纯文字无底板 | **同**（命中区仍 30×30） | 照搬视觉，不牺牲可点性 |

| 顶栏 | 40px 渐变 | **仍然没有** | 第十四轮已删；用户要"视频占满" |

它们都源于同一个物理差异：参考系统播放器的控件能浮在 KMS 平面之上，我们只能占位。

### 14.3 全屏只剩一个「退出」

真机反馈「全屏模式下有两个退出按钮，左一个右一个」。两个都来自底部控制条：

- 左：`cb-back`（`v-if="playFull"`，本轮删除）
- 右：`cb-fs`（全屏态文字原本也是「退出」）

现在：

| 布局 | 退出入口 | 文字 |
| --- | --- | --- |
| 侧栏全屏（16:9，黑边 ≥120） | `.fs-panel` 顶部 `cb-back` | 退出 |
| 侧栏不可用（超宽片源） | 底部条末尾 `cb-fs` | **还原** |

`barMetrics` 也不再传 `back` —— 否则轨道会短 30+3px，右边留一段点不到的空洞。
单测直接守「`class="cb-back"` 在全页只出现一次」。

### 14.4 自检页右栏改成可滚动

X7 上右栏内容约 300px（8 行步骤 128 + 三行信息 48 + 日志 49 + 按钮 26 +
标题/间距），视口只有 280px —— 末行被裁在屏幕外，而且原来是个普通 `div`，
手指划不动，底部四个按钮永远点不到。

现在：外层 `<scroller class="panel">`（固定视口高）+ 内层 `.panel-body`
（自然高、承载 padding），`.foot` 加 `flex-shrink: 0` 防止被压扁。

## 15. 第十九轮：全屏 UI 错乱的根因是「动态 flex-direction + flex-grow」

### 15.1 现象

用户连报两轮：「全屏 UI 错乱」「有多个进度条」「没有修复」。
进全屏后：画面偏在左边、右边一大片黑、控制面板要么没有、要么只露一角；
底部还会多出一条"进度条"。

### 15.2 根因

第十五~十八轮的全屏结构是：

```
.pmid  ← 普通态 flex-direction: column，全屏态靠动态 class .pmid-row 改成 row
  ├── .pstage   视频列（高 280）
  ├── .fs-gap   flex-grow: 1
  └── .fs-panel 控制面板（160x280）
```

两处都不可靠，而且**同时**踩中：

1. **动态 flex-direction**：`:class="fsSide ? 'pmid pmid-row' : 'pmid'"`。
   真机上 `.pmid-row` 没生效，中列仍是 column —— `.pstage` 高 280 把整列占满，
   `.fs-gap` / `.fs-panel` 被排到 y=280（正好在屏外）。屏幕上只剩"画面偏左 +
   右边全黑 + 控件全丢"，这就是「UI 错乱」。
2. **flex-grow 撑间隙**：即使方向切成功，`.fs-gap` 没有显式高度，靠
   align-items: stretch 撑满；组合失效时它宽度为 0，面板贴着画面、右端留空。

「多个进度条」是同一件事的另一半：全屏时左右列被 `v-if` 掉，那块区域没人画，
falcon 又不主动清屏 → 上一屏的控制条像素透出来，看起来像第二条进度条。

### 15.3 现在（第十九轮）

```
.page-body            ← 静态 row（普通态的左列|中列|右列走的就是这条路）
  ├── .fs-pad  (左黑边, 显式宽×视口高, 纯黑)
  ├── .pmid    (视频列, 永远是 column, 宽 = 画面宽)
  ├── .fs-pad  (间隙, 显式宽×视口高, 纯黑)
  └── .fs-panel(面板, 160×视口高, 纯黑)
```

- 四块宽度由 `services/fullscreen.planFullscreen()` 算，
  **left + videoW + gap + panel === 视口宽**，单测直接守这条恒等式；
- 零动态 flex-direction、零 flex-grow、零 flex-shrink 依赖
  （`.fs-pad` / `.fs-panel` 显式 `flex-shrink: 0`）；
- 每块都有像素高和不透明底色，全屏没有"没人画"的区域，残影无从产生；
- 视频列宽度、`.pstage` 宽度、native 盒子的 `width`、`fsPlan.left` 全部同源，
  DOM 与 render-rectangle 不会各算各的。

936×280 上的实际数字（16:9 片源）：

| 块 | 宽 | 说明 |
| --- | --- | --- |
| 左黑边 | 219 | 视频在整屏居中 |
| 视频列 | 498 | 280 高信箱后的宽 |
| 间隙 | 59 | 画面与面板之间 |
| 面板 | 160 | 退出/播放/轨道/±10s/字幕 |

竖屏片源（9:16）：158 | 389 | 229 | 160；21:9 超宽：112 | 664 | 0 | 160；
黑边 < 120 的极宽片源（32:9）退回底部控制条布局（面板不硬塞）。

### 15.4 单测

- `fullscreen: 四块宽度守恒`：7 种比例（16:9 / 1024 宽屏 / 竖屏 / 21:9 /
  32:9 / 4:3 / 尺寸未知）逐个断言「和 === 视口宽」「面板不盖画面」「无负宽」；
- 页面接线：`.fs-pad` 必须是显式宽度的兄弟节点、`.pmid-row` 不许再出现、
  `.fs-pad` 必须铺纯黑。

### 15.5 顺带修掉的一条缝：空台词时的字幕带

`bands.cc` 由 `ccActive`（字幕开 且有 cue）决定，占 18px；但渲染条件是
`bands.cc > 0 && !!subtitleText`。两句之间 subtitleText 是空串 → 带子不渲染，
而那 18px 已经从画面里让出来了：一块**没有像素**的洞。
上一屏底部控制条的像素正好从这里透出来，看起来就是「多出一条进度条」。

现在渲染条件只看几何：`ccBarVisible() { return this.bands.cc > 0; }`，
没有台词时它是一块纯黑（`.cc-bar` 本来就是 #000）。让出的像素 = 画出的像素。

## 16. 第二十轮：全屏改成「用新矩形重开」；下拉系统面板时藏掉平面

### 16.1 为什么放弃「运行期改矩形」

全屏要真的变大，就必须改视频平面的尺寸。之前的做法是
`setVideoRect` → native 更新 `g_w.rect` → 投递一次原地 seek → `build_pipeline`
按新矩形重算 videoscale 的 caps。理论上对，真机上不可靠：

```
videoscale ! video/x-raw,width=<rect.w>,height=<rect.h>
```

这组 caps 是**建管线那一刻**算死的。运行期改 render-rectangle 之后，只要那次
重建没赶上（seek 被合帧、worker 忙、sink 没重新 configure），画面就停在旧尺寸上，
而 UI 已经按新布局摆好了 —— 用户看到的就是「全屏后视频被压缩」。

反过来，**同一台机器用 OPEN 建出来的普通态画面一直是对的**。
所以尺寸变化改走 OPEN：`closeSession` → 用同一份 URL / 音轨 / 设备参数、
只换 `rect` 与 `startMs` 重新开一路。

- 代价：一次 ~0.5s 的起播（黑屏）；
- 收益：caps 与矩形从第一帧就一致，不存在"追不上"的中间态；
- 参数复用 `session.openArgs`，不重新取流（不触发 playurl 阶梯、不换 CDN）。

`play_session.reopenSession(ctx, session, startMs, rect)` 是唯一入口；
页面侧 `setFullscreen(next)` 调它，失败则回滚 UI 并重开回原布局（native OPEN 是
先 teardown 再建，失败的 OPEN 会把旧管线一起带走，不补一次就只剩黑屏）。

互动题面退全屏也走同一个入口（`exitFullForInteract → setFullscreen(false)`）。

### 16.2 下拉状态栏 / 控制中心：把平面藏成 1x1

视频是 KMS overlay 平面，zpos 在 Falcon UI **之上**，系统面板也盖不住它 ——
真机照片里下拉状态栏后，画面浮在控制中心上面。

falcon 拿不到"系统面板展开"的事件，只能靠前后台切换：

| 时机 | 动作 |
| --- | --- |
| `onHide` | `setVideoRect(0,0,1,1)` + 暂停（原有逻辑） |
| `onShow` | 先 `restoreVideoPlane()`（按 `buildVideoRect()` 恢复），再恢复播放 |

- **必须 1x1，不能 0x0**：kmssink 对零宽高既不报错也不隐藏，而是回退成
  "未设置矩形 => 全屏"，反而把整个屏幕盖死（session.c 有实测记录）。
- 藏起来之后把 `_rectKey` 记成 `0,0,1,1`，否则恢复时会被"矩形未变"短路掉。
- 直播不藏：直播恢复要走 live rebuild（1s+），而直播本来没有"停在某一帧"的语义。

## 17. 第二十一轮：全屏不再改视频，只把控件放到右手边

### 17.1 用户判据

> 「视频是由方形压成了边方形（扁方形）……点击全屏后，不对视频位置做任何改动，
> 把进度条、播放、退出全屏、互动视频选项挪到右手边」

这句话把方向定死了：**"不变形"优先于"变大"**。前面两轮（改矩形 / 用新矩形重开）
都在追求"画面上真的变大"，两次都出了变形，说明这条路在这台机器上不可靠。

### 17.2 为什么"改矩形"必然有风险

```bash
videoscale ! video/x-raw,width=<rect.w>,height=<rect.h>,pixel-aspect-ratio=1/1
```

这组 caps 在 **OPEN 那一刻**按矩形算死。之后任何"让平面换尺寸"的做法
（运行期 setVideoRect + 原地 seek 重建，或者关掉重开）都要靠一整条链路追上：
seek 合帧、worker 忙、sink 没重新 configure、caps 重新协商失败 —— 任意一环掉链，
buffer 尺寸就和平面窗口对不上，画面被拉成扁方形。

**不碰它，就绝对不会变形。** 这是唯一有确定性的方案。

### 17.3 新结构：三列不动，只换内容

```
.page-body（静态 row，从未变过）
  ├── .pleft   278×280  全屏时内容是 .pleft-fs（纯黑占位）
  ├── .pmid    457×280  任何状态都一样（视频洞 457×248 + 控制条 32）
  └── .pright  278×280  全屏时内容是 .fsp 控制面板
```

| 项 | 普通态 | 全屏态 |
| --- | --- | --- |
| 左列 | 标题 / 简介 / 点赞收藏 | **纯黑占位**（宽度不变） |
| 中列 | 视频洞 + 字幕带 + 底部条 | **完全相同** |
| 右列 | 评论 / 分P / 合集 / 收藏 | **控制面板** |
| 视频矩形 | `bandBox(中列)` | `bandBox(中列)`（同一份） |
| native 调用 | — | **零** setVideoRect，零 reopen |

关键点：左列**不能 v-if 掉**。它一旦消失，中列会左移，视频洞的 x 就变了 ——
而 KMS 平面还按老矩形出画，屏幕上是"画面跑到左边、右边一块黑"。所以左列
保留原宽度，只把内容换成纯黑。

### 17.4 面板内容（278×280）

| 行 | 高 | 内容 |
| --- | --- | --- |
| 退出全屏 | 30 | `.fsp-exit`，粉字，整行可点（全屏唯一出口） |
| 播放 | 34 | 30 粉圆播放键 + `当前时间 / 总时长` |
| 轨道 | 26 | 4px 槽 + 12px 白滑块，宽 = 面板宽 − 24 |
| 步进 | 30 | `-10s` / `+10s` / `字幕`（三个 62×26） |
| 互动 | 剩余 | 标题 + 选项列表（可滚），收起时给「‹ 显示本段互动选项」 |

- 子元素全部**显式像素宽**（`fsInnerW`），靠 `.fsp` 的 `align-items: center` 居中。
  容器上不加左右 padding —— falcon 的盒模型没有文档保证，padding 一旦额外加宽，
  278 的面板会被撑到 302 顶出右列（控制条那 12px 超宽的旧账就是这么来的）。
- 面板高取 `L.playRight.height`（与右列容器同源），不是视口高：容器若比视口矮，
  按视口高画会裁掉底部，而底部正好是互动选项。

### 17.5 互动选项不再强制退全屏

旧逻辑（`exitFullForInteract`）是：题面出现在右列，而全屏态右列被让位了，
所以必须先退全屏，否则会出现"片段停住、屏幕上一个可点的东西都没有"的死局。

现在右列就是面板，选项直接画在面板下半部分，同一个位置可点。`exitFullForInteract`
保留成"确保控件可见"的空操作，避免调用点改动。

### 17.6 单测

- `fullscreen: 全屏不改视频几何`：页面不许出现 `planFullscreen / fsPlan / fsFit /
  fsVideoW / fs-pad / fs-panel`；`midStyle()` 必须恒返回 `L.playMid`；
  `midW()` 必须恒等 `L.num.videoW`；`barH` 必须恒 `seekH`；
  `setFullscreen` 里不许出现 `reopenSession`；面板四个类名 + 样式必须存在。
- `几何恒定`：`applyVideoGeometry` 里不许再给 `full-*` 开绿灯，唯一放行原因是 `cc`。
- 删除了原 `planFullscreen` 四块守恒用例（那份几何已随文件删除）。

## 18. 第二十三轮：退后台不再"藏平面再恢复"；本地栏按反馈移除

### 18.1 真机症状

> 「开始时正常，一旦我上滑打开状态栏然后随便打开一个界面，再回退视频以后就变扁了」

照片里画面被拉成一条横带。这是**唯一**还有 `setVideoRect` 参与的路径。

### 18.2 根因

第二十轮的做法是：

| 时机 | 动作 |
| --- | --- |
| `onHide` | `setVideoRect(0,0,1,1)` 把平面藏起来 |
| `onShow` | `buildVideoRect()` → `setVideoRect(正常矩形)` 恢复 |

两次都是**运行期改矩形**。X7 的管线里有

```
videoscale ! video/x-raw,width=<rect.w>,height=<rect.h>
```

改矩形只能靠 native 投递一次原地 seek 去重建管线、追新 caps。追不上时
buffer 尺寸与平面窗口就对不上 —— 画面被压扁。这和第二十轮修全屏压缩是
**同一个物理原因**，当时只把全屏改成了"重开"，忘了这条前后台路径。

### 18.3 现在

| 时机 | 动作 |
| --- | --- |
| `onHide` | `hideForBackground()`：记 `pos` / 暂停态 → **`closeSession()`** → 停轮询、停保活 |
| `onShow` | `reopenForForeground()`：等关闭任务落地 → `buildVideoRect()` → **`reopenSession()`** |

- 「关闭视频」这本来就是用户最初的要求（下拉状态栏时别让画面浮在系统面板上），
  现在它是真的关，而不是"缩成 1 像素"；
- 重开时 caps 与矩形从第一帧就一致，不存在追不上的中间态；
- 代价：回前台一次 ~0.5~1s 起播。换来的是**任何前后台切换都不会改变画面比例**；
- 直播不关（没有"停在某一帧"的语义，且 live rebuild 要 1s+ 会换 CDN），
  仍走原来的"暂停 + 恢复播放"。

竞态处理：`_bgClosed` 在 `hideForBackground` 里**同步**置位（不等 closeSession
跑完），`_bgTask` 保存关闭 Promise；`reopenForForeground` 先 `await _bgTask`
再 OPEN —— native 的 OPEN 是先 teardown 再建，上一个会话没拆完就 OPEN 会撞
`PLAYER_ALREADY_RUNNING`。

### 18.4 仍然会改矩形的两处（已知，未改）

1. **开/关 CC 字幕**：字幕带占 18px，必须真的改矩形。低频操作，且真机验证过；
2. **评论输入法**：拉起系统输入法前把平面藏成 1x1（否则输入框被视频盖住），
   关闭后恢复。它同样有"追不上"的风险，但只发生在用户主动发评论时，
   与本次反馈的路径不同，先留着观察 —— 如果真机上"评论完画面变扁"，
   就把它也改成关会话 + 重开。

### 18.5 关于"参考系统播放器的进度条盖住视频"

用户指出参考系统播放器的进度条是**浮在画面上**、背景虚化透明的。这一点我们做不到，
原因在 `play_chrome.js` 文件头写了很多次：视频是 KMS overlay 平面，**zpos 在
Falcon UI 之上** —— UI 画上去会被画面盖住，不是"半透明"，是"完全看不见"。

所以我们的控制条**必须占真实像素**（32px），视频矩形相应短 32px。但请注意：
短的是"盒子的高度"，**宽高比没变** —— 457×248 的盒子里做 16:9 信箱得到
441×248，比例仍然是 16:9。

真机上看到的"变扁"从来不是这个设计导致的，而是 caps 与矩形不一致（§18.2）。

  `isLocalPlay` / tick 时长回填 / 左列三连隐藏 / 右列本地信息块全部删除；

- 文档：`docs/local-video.md` 删除，README 条目删除；
- **native 的 `listFiles` 保留**（不被调用就没有开销），注释里注明当前 JS 未使用 ——

## 19. 第二十四轮：删掉自适应分辨率，控制条改成浮在画面上

### 19.1 用户要求

把机型参数全部写死（X7P / X6P 两张常量表，删掉自适应逻辑）；分辨率与参考
系统播放器一致；隐藏进度条后分辨率不变、屏幕不要有大黑边；进度条风格照参考
系统播放器界面上的照片还原。

三件事：① 机型参数写死；② 分辨率与参考系统播放器一致；③ 控制条盖住画面，
隐藏后不留黑边、比例也不许变。

### 19.2 写死：`device_profile.js` 只剩两张表

删掉的东西（**不要再加回来**）：

| 删掉的 | 为什么 |
| --- | --- |
| `readFalconEnv()` | 从 `$falcon.env` 猜视口，还要排除"报成面板尺寸"的固件 |
| `normalizeEnvViewport()` | 竖屏旋横、上下限钳制 —— 一套猜谜 |
| `storage` 的 `bili_device_profile` 覆盖 | 用户点一次 A/C 档就永久写进 `swScale:1`，重装也绿幕 |
| `RATIO_MODES` / `cycleRatioMode` / `currentRatioMode` | 自检页四档，调的是"缩放方式"，从来没解决过几何 |
| 自检页的「A/B/C/D」按钮 | 同上，现在连参数都不给改了 |

现在只有：

```
X7P  936x280  面板 480x960  偏移 0    plane auto   swScale 2（竖帧）
X6P  960x266  面板 480x960  偏移 107  plane 76     swScale 0（硬件缩放）
```

`buildProfile({})` 恒等 X7 Pro；`buildProfile({ name: 'x6p' })` 拿 X6 基线。
`env` / `override` 传进来会被**忽略**（不报错，也不生效）。

分辨率与参考系统播放器一致：它的面板列 × 面板行是 `280x936`，我们的视口是
`936x280`，同一个数、同一套旋转。

### 19.3 控制条浮在画面上（几何）

参考系统播放器的 bottom-bar 带
`linear-gradient(to top, rgba(0,0,0,0.8), transparent)` 背景 —— 它明显准备
透出背后的画面。这一轮照此还原，**只改一处几何**：

```
旧：视频矩形 = 中列全高 − 字幕带 − 控制条(32)
新：视频矩形 = 中列全高 − 字幕带
```

DOM 一个像素都没动：

```
.pmid (280)
  ├── .pstage (248 = 视频洞)      ← hole 只挖 248
  ├── .cc-bar (18，有字幕时)
  └── .chrome-bar (32)            ← 半透明黑，盖住视频最后 32 行
```

也就是说：**视频平面多画 32 行到控制条底下，DOM 完全不重叠**。

为什么不重叠：falcon 的 `position:absolute` / `z-index` 不可靠（全仓铁律），
但 native 的 `render-rectangle` 与 DOM 的 hole 本来就不必等大 —— 视频平面是
硬件层，尺寸只由 native 决定。这是这一轮最关键的发现：**要"盖住"根本不需要
DOM 重叠，只需要让 native 的矩形比 hole 大**。

### 19.4 怎么保证"怎么改都不扁"（**已被 §20 推翻，见下**）

> ⚠️ 这一小节当时的结论是错的。`videoscale add-borders=true` 补出来的"边"
> 是 YUV 全 0，NV12 下就是**绿色**。横屏 16:9 只补 11px 看不出来，竖屏要补
> 150px，真机直接两片绿幕。第二十五轮已回退，正确做法见 §20。

参考系统播放器把信箱交给 `kmssink force-aspect-ratio=true`，自己只给外框。
我们当时试的是 `videoscale add-borders=true` —— 不成立。

### 19.5 隐藏控制条 = 整条不渲染（**已被 §22 推翻，见下**）

> ⚠️ 这个做法正是第二十七轮的 bug 来源：falcon 不主动清屏，整条不渲染后
> 旧黑条像素留在 framebuffer 上，用户看到「视频下方原进度条的位置有黑边」。
> 正确做法见 §22。

`chromeBarVisible` 从 `bands.bar > 0` 改成 `bands.bar > 0 && ui.chrome`。
收起时整条不渲染，`.pmid` 底部那 32px 是透明的（`.page-live` 根节点透明），
视频从这里完整透出来 —— 隐藏前后**矩形不变**，画面也不会有黑带。

底部 32px 的点击由 `.pmid-tap`（alpha=0 的命中区）接管，点一下重新唤出控件。

### 19.6 控制条视觉（对照参考系统播放器）

| 项 | 参考系统播放器 | 我们 |
| --- | --- | --- |
| 条高 | 55（936 宽） | 32（457 宽，比例接近） |

| 播放键 | 50 粉底圆 + 白图标 | 30 粉底圆 + 18 白图标 |

falcon 没有可靠的 `linear-gradient`，所以用单色 0.82 近似：0.82 让下面 18%
的画面透出来，既有"盖住"的观感，又保证 `#DDDDDD` 的字和 0.3 白的轨道读得清

## 20. 第二十五轮：绿幕、点屏幕不隐藏、全屏下方黑边

### 20.1 竖屏绿幕 = add-borders 补的是 YUV 0

第二十四轮把信箱交给 `videoscale add-borders=true`，以为它会补黑边。
真机（竖屏 9:16 稿件）左右各 150px **纯绿**：

```
NV12 的 (Y,U,V) = (0,0,0) → RGB ≈ (0,135,0)
```

videoscale 补边时按 `memset(0)` 填，不是按色彩空间的黑（Y=16,U=V=128）。
横屏 16:9 在 457x280 的框里只补上下 11px，肉眼看不出来，所以第一轮没暴露。

**修法**：回退 add-borders，信箱重新由 JS 算
（`buildVideoRect` / `openVideo` 改回 `playVideoRectsFor`）。
矩形 = 画面本身，plane 窗口与 buffer 等大，**没有边可补**；
画面之外的黑色由 Falcon 的 UI 层提供（`<hole>` 之外的 fb 黑）。

这不会让"变扁"回来：矩形只由 `bands`（几何）和片源尺寸决定，播放期间恒定，
caps 与 render-rectangle 从第一帧就一致。

### 20.2 点屏幕不隐藏

`onVideoTap` 原来有一条「暂停态点画面 = 继续播放」。结果在暂停状态下怎么点
都只是播放/暂停，控件永远收不起来 —— 用户反馈「进度条点击屏幕无法隐藏」。

现在点画面**统一是显隐**，播放/暂停只由控制条那颗粉键负责。

### 20.3 全屏下方黑边 = 空的控制条

`chromeBarVisible` 原先只看 `ui.chrome`。全屏态控件都在右列面板里，中列底部
这条 32px 仍然渲染（内容为空）→ 一条纯黑带，就是用户说的「全屏模式视频下方
存在大黑边」。现在加上 `&& !playFull`：全屏态整条不渲染，画面完整透出。

### 20.4 与参考系统播放器的隐藏/显示对比

用户给的两张参考系统播放器截图（一张有进度条、一张没有）说明了目标：

- 两张的**画面位置和大小完全一样**；
- 有进度条那张，条是半透明浮在画面上，画面不受影响；
- 没有进度条那张，画面底部一点黑边都没有。

对应到我们的实现：

| 状态 | 视频矩形 | 控制条 | 画面 |
| --- | --- | --- | --- |
| 显示控件 | 恒定（fit 到中列全高） | 半透明黑 32px 浮在底部 | 底部被盖 32px |
| 隐藏控件 | **不变** | 整条不渲染 | 完整透出，无黑带 |

## 21. 第二十六轮：全屏重做 —— 真正铺满整个屏幕

### 21.1 用户反馈

> 没一个能用……现在在全屏模式下有两个进度条，点击无法隐藏进度条，
> 视频还是小，**全屏视频在进度条没有显示的情况下需要占满屏幕**。

第二十一轮那套「全屏只是纯 UI 换装、视频一个像素不动」到这里作废：它把
画面锁死在中列 457 宽里，左右各 240px 黑，正是「视频还是小」。

### 21.2 三个直接原因

| 现象 | 原因 |
| --- | --- |
| 两个进度条 | 中列底部 32px 的 `chrome-bar` / 残留像素 + 右栏 `fsp` 各一条 |
| 点画面隐藏不了 | 全屏控件在右栏 `fsp`，**不受 `ui.chrome` 控制**；点画面只影响中列 |
| 视频小 + 下方黑边 | 矩形始终是中列 457×280；底部 32px 一直被空条占着 |

### 21.3 全屏 = 整屏矩形 + cover 裁切

936×280 是 3.34:1，16:9 片源按 contain 最多只有 498×280 —— 无论视频区
给多宽都是 498。要「占满」只能 **cover**：等比放大到铺满，再裁掉多余部分。

```
物理窗口 tw x th = 280 x 936
解码后帧比例 r = vh/vw（16:9 → 0.5625）
tw/th < r → 按高铺满，左右各裁 (th*r - tw)/2 = 122
tw/th > r → 按宽铺满，上下各裁 (tw/r - th)/2
```

`device_profile.coverFrameFor()` 算裁切量，经 `openArgs.cropX/cropY`
→ `player.deviceArgs` 第 21/22 位 → `jsapi_player2.c` → `session.c`：

```diff
- videoscale ! video/x-raw,width=tw,height=th ! kmssink(render-rectangle=tw x th)
+ videoscale ! video/x-raw,width=tw+2cx,height=th+2cy !
+ videocrop left=cx right=cx top=cy bottom=cy !
+ kmssink(render-rectangle=tw x th)
```

仍是 1:1 贴 buffer，不依赖平面缩放能力，也不产生 `add-borders` 的绿边。
**竖屏片源（vw <= vh）不 cover**（会裁掉 80%），回落 contain。

### 21.4 三列全透明

全屏时视频矩形跨过整个视口，所以左/右列连**容器底色**都必须透明：

- `.pleft` / `.pright` 带 `@nav-background` → 用内联 `backgroundColor:rgba(0,0,0,0)` 覆盖
- `.pleft-fs` / `.fsp` / `.fs-clear` 背景同为全透明
- 中列 `<hole>` 280 全高

任何一块留底色，就会把视频挖走 208 / 271 px —— 那正是「左右大黑边」。

### 21.5 只剩一条进度条，且能隐藏

- 中列在全屏态 **不画** `chrome-bar`（`chromeBarVisible` 加 `!playFull`），
  也不留 32px 空洞：`videoBoxStyle` 在控件收起时把视频洞补到 280。
- 唯一进度条在右栏 `fsp`，且 `v-if="ui.chrome"`。
- 点画面 → `setChrome(false)` → 右栏换成 `.fs-clear` 透明占位（防残影）、
  中列洞 280、左列透明 → **整个视口只剩视频**。
- 再点 → 控件回来。

### 21.6 代价

1. **进出全屏要重开一路流**（矩形从 457×257 换成 936×280，caps 必须重建），
   一次约 0.5~1s 起播。这是不做「运行期改矩形」的必然代价。
2. **16:9 会裁掉上下约 47% 的画面**（3.34:1 屏 + 保持比例的物理结果）。
   竖屏稿不裁，代价是仍有左右黑边。若之后要改成 contain + 黑边，
   `coverFrameFor` 里把横屏分支也走 `contain()` 即可，一行。


## 22. 第二十七轮：只修视频下方原进度条位置的黑边

### 22.1 用户澄清

> 我说视频下方原先进度条的位置又黑边，左右的黑色区域不用管。

上一轮把「占满屏幕」理解成左右铺满，做了整屏 cover / 三列透明，方向跑偏。
用户抱怨的始终是**屏幕底部原进度条那 32px 的一条黑带**；左右黑边
（16:9 或 9:16 片源的信箱）明确不用管。

### 22.2 根因：不是视频矩形，是 falcon 不清屏

第二十四轮起 `chromeBarVisible` 变 false 时把整条 `.chrome-bar` `v-if` 掉了：

```
显示控件： [ 视频洞 248 ][ .chrome-bar 32 ]   ← 画了一条 rgba(0,0,0,0.82) 黑带
隐藏控件： [ 视频洞 248 ][   没有 DOM   ]   ← 那 32px 没有任何绘制
```

falcon **不主动清屏**（第十九轮字幕带踩过同一个坑）：没有 DOM 绘制就不会
擦掉上一次的像素，于是那条半透明黑带一直留在 framebuffer 上 —— 看起来
就是「进度条隐藏了，但下面那条黑边还在」。

第二十四轮试过补一个 `.pmid-tap`（`rgba(0,0,0,0)` 的普通 div）也没用：
透明 div 只是「这次不画」，同样擦不掉旧像素。第十九轮的正确解法是
**必须有一个真 `<hole>`** —— 它把这块 fb 交还给底下的视频平面，旧像素
被视频帧覆盖掉。

### 22.3 修法：32px 恒有 DOM，二选一

```html
<div v-if="chromeBarVisible" class="chrome-bar" :style="ctrlBarStyle">…控件…</div>
<hole v-if="!chromeBarVisible" class="bar-hole" :style="ctrlBarStyle" @click="onVideoTap"/>
```

| 状态 | 底部 32px | 效果 |
| --- | --- | --- |
| 显示控件 | `.chrome-bar` 半透明黑 | 盖在画面底部（参考系统播放器有进度条那张） |
| 隐藏控件 / 全屏 | `<hole class="bar-hole">` | 真挖孔，画面完整透出（参考系统播放器无进度条那张） |

两者共用 `ctrlBarStyle`（`midW × bands.bar`），逐像素等高。

### 22.4 几何回到恒定

第二十六轮曾让 `videoBoxStyle` 在收起时吃到 280 —— 那样 `280 + 32 = 312`
撑出 280 高的中列，和 native 的 280 矩形不再同源。现在改回：

```
DOM     : .pvideo 248 + .cc-bar 0 + 底部 32 = 280（恒定）
native  : bandBox(area 280, { top, cc, bar: 0 }) = 457×280（不扣 bar）
```

即 **native 矩形比 DOM 的视频洞多 32px**，画面一直画到那条带子底下：
带子半透明时透出 18%，换成 `<hole>` 时完整透出。这正是参考系统播放器两张截图
的关系 —— 有/无进度条，画面位置与大小完全一样，隐藏前后矩形一个像素不变。

### 22.5 左右区域一律不动

用户明确「左右的黑色区域不用管」，所以第二十六轮的整屏 cover、三列透明
等一律保留原样，本轮只改中列底部这 32px。

### 22.6 需要与信箱黑区分

普通态 16:9 在 457×280 的框里 fit 成 457×257，画面上下各约 11px 是
**片源比例带来的信箱黑**，与本节修的那条 32px 残留黑带不是一回事。
按用户说明，这类黑边（左右及上下）不在本轮处理范围内。

## 23. 第二十八轮：全屏 UI 错乱 —— v-else 链 + 透明容器

### 23.1 现象（真机截图）

点全屏后：

- **左列**仍是普通态的标题 / UP / 简介 / 点赞投币收藏三个按钮；
- **右栏**评论区（评论列表、"未登录·不能评论"、"发送"）与全屏控制面板
  （"‹ 退出全屏"、粉色播放键、00:00、进度条）**叠在同一块像素上**。

视频本身位置正常、比例正常 —— 所以这不是几何问题，是**分支没切干净**。

### 23.2 根因一：falcon 接不住跨标签的 v-else 链

右栏原本是四个 `<template>` 组成的 `v-if → v-else-if → v-else-if → v-else` 链，
左列是 `<div v-if="playFull"> → <template v-else>`。**跨标签名时 falcon 对
v-else 的支持不稳** —— 这一点项目里早就记录过（index.vue 第 746 行注释：
「三个页签用三个独立 v-if（不是 v-else-if 链）：falcon 对跨标签标签名不同的
v-else 链支持不稳」），但右栏没有照做。

结果 `playFull=true` 时评论区那个 `v-else` 分支照样渲染，与全屏面板同时存在。

**修法：四条分支改成显式互斥的独立 `v-if`，条件写全**：

```diff
- <template v-if="playFull">                 …全屏面板…
- <template v-else-if="interact.visible">   …互动…
- <template v-else-if="favOverlay">         …收藏夹…
- <template v-else>                         …评论区…
+ <template v-if="playFull">
+ <template v-if="!playFull && interact.visible">
+ <template v-if="!playFull && !interact.visible && favOverlay">
+ <template v-if="!playFull && !interact.visible && !favOverlay">
```

左列同样把 `<template v-else>` 改成 `<template v-if="!playFull">`；
`.fsp` / `.fs-clear` 的 `v-if`/`v-else` 也改成两个独立 `v-if`。

### 23.3 根因二：透明容器不擦除旧像素

第二十六轮为了「视频铺满左右」把 `.pleft-fs` / `.fsp` / `.fs-clear` 以及
`.pleft` / `.pright` 容器都改成了 `rgba(0,0,0,0)`。falcon **不主动清屏**
（§22 同一个坑）：透明只是"这次不画"，上一屏的信息栏 / 评论区像素原封不动
留在 framebuffer 上，新面板再叠上去 → 错乱加重。

**修法**：三块全恢复 `#000000`，并删掉 `leftColStyle` / `rightColStyle`
那两个内联透明覆盖。要擦掉旧像素必须真的画一层不透明黑。
用户已明确「左右的黑色区域不用管」，所以黑底没有代价。

### 23.4 顺带：全屏几何退回中列

第二十六轮的「整屏 936×280 + cover + `reopenSession` 重开」在这张截图里
**并没有生效**（画面仍在原中列位置、大小与普通态一致），却带来 0.5~1s 黑屏
和重开失败的风险；左右列恢复黑底后，整屏矩形更是会被黑块盖住、只露出中间
被裁掉 47% 的一小条。

所以这一轮一并退回第二十一轮的常量几何：

| | 现在 |
| --- | --- |
| 全屏切换 | 纯 UI，**不重开、不下发 setVideoRect** |
| `bandPx().full` | 恒 `false` |
| `buildVideoRect` / `openVideo` | 只有中列一种盒子，`playVideoRectsFor` fit |
| `cropX` / `cropY` | 恒 0（native 的 `videocrop` 能力与参数链保留，但不启用） |

左右黑区域按用户说明不处理。

### 23.5 保留的修复

- §22 底部 32px 的 `<hole class="bar-hole">`（隐藏控件时擦掉旧黑条）
- 全屏唯一进度条在右栏 `.fsp`，`v-if="ui.chrome"` 随点画面显隐
- 中列全屏态不画第二条进度条（`chromeBarVisible` 带 `!playFull`）

## 24. 第二十九轮：横屏视频左侧那条绿线

### 24.1 现象

横屏 16:9 稿件，画面左边缘一条**从上到下的纯绿细线**（约 1~2 物理像素）。
画面本身完整、比例正常，只有边缘那一列。

### 24.2 根因：物理矩形起点是奇数

中列 457×280 里 fit 出逻辑 {457×257}，经 `logicalRectToPhysicalRect`
（rotation 270，宽高互换）得到：

```
物理 { x: 12, y: 271, width: 257, height: 457 }
```

native 的 `normalize_video_rect` 只把**宽高**对齐到偶数（256 / 456），
**起点 y=271 仍是奇数**。NV12 的 UV 平面按 2×2 采样，平面起点落在奇数行时
chroma 相位错位，最边缘一列取到 YUV 全 0 —— 也就是绿色（同 §20.1 的
`add-borders` 绿边是同一类问题：YUV 0 ≠ 黑）。

### 24.3 修法：四个数全对齐

`src/services/screen.js` 的 `logicalRectToPhysicalRect` 是**唯一**的物理
换算出口（主页、自检页、探针都走它），在出口统一对齐：

```js
x: (y + 1) & ~1,                        // 向上取偶，不把上一列无效 chroma 包进来
y: (panel.height - (x + w) + 1) & ~1,
width: Math.max(2, h & ~1),             // 向下取偶
height: Math.max(2, w & ~1)
```

最多挪 1px，肉眼无感；但四个数全偶之后 chroma 相位一定对齐。

`native/csrc/session/session.c` 的 `normalize_video_rect` 同步补了 x/y
兜底（日志文案改成 `aligned to even x/y/size`），防止别的调用方绕过 JS。

### 24.4 对齐后的值

| 场景 | 对齐前（物理） | 对齐后（物理） |
| --- | --- | --- |
| X7 16:9 中列 | `{12, 271, 257, 457}` | `{12, 272, 256, 456}` |
| X7 9:16 中列 | `{0, 420, 280, 158}` | 不变（本来就全偶） |
| X6 16:9 视频区 | `{0, 299, 240, 427}` | `{0, 300, 240, 426}` |
| X6 9:16 视频区 | `{0, 445, 240, 135}` | `{0, 446, 240, 134}` |
| X6 直播 16:9 | `{1, 278, 264, 469}` | `{2, 278, 264, 468}` |

### 24.5 守卫

`test/run.js` 新增「物理矩形四边必须偶数」用例：5 种片源 × 3 种盒子，
x/y/width/height 必须全部 `% 2 === 0`，且对齐前后尺寸差不超过 1px。

### 24.6 第二十九轮补：只对齐偶数没用，plane 尺寸要 16 对齐

第一版只把 x/y/width/height 对齐到**偶数**，用户反馈「完全没有修复」。
那版的推论（chroma 相位错位）只说对了一半 —— 真正的机制是 **plane 被撑大**：

```
物理矩形 { x:12, y:272, width:256, height:456 }
                                     ↑ 456 = 16 × 28.5，不是 16 的整数倍
VOP2 把 plane 高度向上撑到 464
多出的 8 行没有任何 buffer 写入 → 未初始化内存 → YUV 全 0 → 绿
旋转 270 后，plane 的高度方向 = 屏幕的水平方向 → 画面最左边 8px 绿
```

和 §20.1（`add-borders` 补边）、§21 注释里「plane 未初始化内存」是同一个
物理事实：**YUV 0 不是黑，是绿**。

修法（`device_profile.js` 的 `alignPlane16`）：

- **只对 X7**（`swScale != 0`，走 videoscale + 自选 overlay 平面）。
  X6 是 kmssink 硬件缩放，rect 给多大就填多大，按 16 收边只会白白缩小画面。
- **只对横屏**（`vw >= vh`）。竖屏 158 收到 144 要损失 9%，用户没报过竖屏绿线。
- width / height **向下**对齐到 16，差值**居中补偿**（黑边均分两侧）。

对齐后的值：

| 场景 | 物理矩形 |
| --- | --- |
| X7 16:9 中列（457×280 框） | `{12, 276, 256, 448}`（原 456 → 448） |
| X7 21:9 | `{44, 276, 192, 448}` |
| X7 9:16 竖屏 | `{0, 420, 280, 158}`（不动） |
| X6 16:9 | `{0, 302, 236, 420}`（不动） |

代价：横屏画面高度少 8px（约 1.8%），洞内上下各多 4px 黑。可接受。

### 24.7 如果还不行

需要自检页「日志」里的这两行（`pb2_logf`）：

```
video: videoscale -> <w>x<h> ... (panel rect <w>x<h>, rotate=270, ...)
OPEN rect: logical=<x,y,w,h> -> panel <x,y,w,h> (offset=0)
```

这两行能确认 ① 送进 kmssink 的 buffer 尺寸、② render-rectangle 实际值。
如果两者一致且都 16 对齐，绿线还在，那就是 plane 的**起点**（x/y）也被
驱动对齐了 —— 下一刀要把 x/y 也 16 对齐。

### 24.8 第三版：起点也要对齐，横竖屏都用 16 网格

§24.6 只对齐了 width/height，真机结果是**绿线换了个位置**：

| 版本 | 改动 | 真机结果 |
| --- | --- | --- |
| v1 | x/y/w/h 对齐**偶数** | 绿线原样（456 仍是 16 的半格） |
| v2 | w/h 对齐 **16**，x/y 只偶数 | 横屏：左侧消失，**上下**各出现一条；竖屏：仍在左侧 |
| v3 | **四边全部**落到 16 网格 | 横屏竖屏都消失 |

v2 的"绿线搬家"说明了机制：驱动（VOP2）把 `render-rectangle` 的 x/y 也一起
圆整到 16 边界。横屏 v2 的矩形是 `{x:12, y:276, w:256, h:448}` —— h 已经在
网格上，但 **x=12 不在**，plane 从 16 开始、高仍 256，末尾 4 行没有 buffer
写入 = YUV 0 = 绿。旋转 270 后 plane 的 x 方向对应**屏幕的垂直方向**，
所以绿线从左侧跑到了上下。

v3 的规则：

```
起点：snap 到最近的 16 倍数
尺寸：在 16 网格里找一组与源比例最接近的（不能独立取整！）
```

尺寸为什么必须成对取：竖屏 280×158 若各自向下取整得 272×144，比例从
1.772 变成 1.889，画面会被横向拉 6.6%。正确做法是以高度为基准逐格往下试，
第一个比例误差 ≤1% 的组合：竖屏 → 256×144（等比 0.914，误差 0.34%）。

最终值（X7，中列框）：

| 片源 | 物理矩形 | 相对旧尺寸 |
| --- | --- | --- |
| 16:9 | `{16, 272, 256, 448}` | 高度 -1.8% |
| 9:16 | `{16, 432, 256, 144}` | 整体 91% |
| 21:9 | `{48, 272, 192, 448}` | 宽度 -0% |
| 4:3 | `{16, 336, 256, 336}` | 高度 -9.7% |

X6 完全不参与（kmssink 硬件缩放，rect 给多大填多大，收边只会白缩画面）。

代价：竖屏画面缩到 91%，四周多几像素黑；换来的是所有比例都不再有绿边。
如果以后要找回这 9%，正确方向是让 `videoscale` 输出 16 网格尺寸、再用
`videobox fill=black` 把画面贴进更大的窗口 —— 不是把矩形放回非网格。

### 24.9 v4：不缩画面，把绿边涂黑（当前方案）

用户提了更对的思路：

> 能不能不更改所有的分辨率，把绿边的绿色改为黑色

绿的本质是 **plane 上有一段区域没有 buffer 写入**（YUV 全 0）。既然无法保证
窗口一定落在 16 网格上，那就反过来：**让窗口比画面大**，多出来的部分由我们
主动填成黑色。这样画面尺寸一个像素都不用改。

实现（`native/csrc/session/session.c`）：

```
normalize_video_rect():  向上对齐到 16（nx/ny 居中回退），记录 g_w.pad_x/pad_y
video_post_rate_desc():  videoscale 输出「画面原尺寸」
                         ! videobox left/right/top/bottom=pad fill=black
                         ! kmssink(render-rectangle = 16 网格窗口)
```

- `fill=black` 是 **YUV 16/128/128**，真正的黑；`add-borders` 那种 YUV 0 是绿。
- 只在 `swScale == 2`（X7 竖帧、不互换）时启用，pad 是在旋转后的物理坐标里量的。
- 每次 `normalize_video_rect` 开头清零 `pad`，X6 路径（`swScale=0`）不会误插。
- `videobox` 是 gst-plugins-good 的核心元素；若固件没带，日志会打
  `videobox unavailable -> stretch`，退化为直接拉伸到窗口（最多 1.9%），
  不会黑屏。

JS 侧相应回退：`device_profile.js` 只保留 NV12 的**偶数**约束，16 网格
与补边全部交给 native。所以：

| 片源 | JS 下发（物理） | native 窗口 |
| --- | --- | --- |
| 16:9 | `{12, 272, 256, 456}` | `{12, 268, 256, 464}`，pad 0/4 |
| 9:16 | `{0, 420, 280, 158}` | `{0, 418, 288, 160}`，pad 4(左侧被 0 钳掉)/1 |

画面尺寸 100% 保留（对比 v3 竖屏 91%），代价是窗口向外多占最多 15px ——
多出来的是黑边，压在相邻列的边缘上，观感与信箱黑一致。

**为什么不是简单地给 plane 设背景色**：`kmssink` 没有 background 属性，
VOP2 的 layer background 也不在 GStreamer 的公开接口里；把内容画进 buffer
是唯一可控的路径。

### 24.10 v5：上下绿线=源帧宏块 padding，裁源 + 竖屏放大

**现象**（真机截图）：横屏 16:9 画面**上下各一条**绿线，左右干净；竖屏正常。

左右干净说明 §24.8 的 16 网格已生效（plane 未写入那条路已经堵住）。
剩下的绿来自**源帧**：1080 在 H.264 里按 16 宏块对齐是 **1088**，多出的
8 行没有任何图像内容（YUV 0 = 绿）。旋转 270 后它们落在竖帧的宽度方向，
缩放到窗口高度 448 之后正好是上下各约 3px。

**修法**：`videoscale` 之前插 `videocrop left=6 right=6`：

```
videorate ! video/x-raw,framerate=… ! videocrop left=6 right=6 ! videoscale …
```

- 8 行 padding 无论落在哪一侧都会被覆盖（6+6 > 8），不用赌旋转方向；
- 总宽 1088 → 1076，与原 1080 只差 0.37%，画面比例几乎无损；
- 只对 `swScale == 2`（X7）生效。

**失败降级（这次的硬要求）**：`do_open` 里带裁切的管线建失败时，
自动 `teardown` 后去掉 `videocrop` 重建一次：

```c
int built = build_pipeline(req, 0);
if (built != 0 && g_w.sw_scale == 2 && !g_w.vcrop_failed) {
    g_w.vcrop_failed = 1;   /* 本次运行期不再试 */
    teardown_pipeline();
    built = build_pipeline(req, 0);
}
```

`vcrop_failed` **不随 OPEN 重置**：一台机器一旦证明建不起来，就不再每次
起播都多赔一次失败重建（那会让起播慢一倍）。最坏结果 = 回到"能播、有绿边"，
绝不再出现 v4 那种"播放失败 + 退不出应用"。

**竖屏放大**（用户要求）：`fit16Size` 的起点改成——

- 原高度离上一个 16 倍数 ≤4px → 向上取整；否则向下。
- 误差阈值放宽到 3%。

| 片源 | 之前 | 现在 |
| --- | --- | --- |
| 16:9 | 256×448 | 256×448（不变） |
| 9:16 | 256×144 | **288×160**（+25%，横向拉伸 2.8%） |
| 21:9 | 192×448 | 192×448 |
| 4:3 | 256×336 | **272×368**（+12%） |

竖屏 288 比洞宽 280 多 8px，右侧压住右列边缘一点（画面内容，不是黑边）；
这是"放大"的必付代价。

### 24.11 v6：绿线是三边一圈，改成四边一起裁

**现象**（真机照片）：绿线不是单边，而是沿画面上、右、下三边各 2~3px 的一圈，
**紧贴画面内容**，绿线外面才是 UI 黑底。这一点很关键：

- 如果是平面比 buffer 大，绿线会和画面之间隔着一段黑；
- 绿线紧贴内容、外面才是黑，说明绿是**送进平面的最后一圈像素**本身。

来源仍在源帧侧：1080 按 16 宏块对齐是 1088（多 8 行 YUV 0），部分转码稿
还会在宽/高上补到宏块边界。v5 只裁了左右各 6，上下没裁，所以绿线换了个
边又露出来。

**修法**：`videocrop left=16 right=16 top=16 bottom=16`，四边各 16：

- 覆盖 8 行宏块 padding + 常见转码补边，无论 padding 落在哪一侧；
- 1080p 下只损失约 1.5%~3% 画幅，肉眼无感；
- 裁切在 `videoscale` **之前**，缩放后不会再有半像素残边；
- 仍然只对 `swScale == 2`（X7）生效，并保留「管线建失败自动去掉裁切重试」
  的兜底（`vcrop_failed` 不在 OPEN 时重置）。

**新增诊断**：首帧到达时打一行 sink 实际协商到的 caps：

```
video: sink caps <w>x<h>, render-rect <x,y,w,h>
```

如果两者相等而绿线仍在，就证明绿来自源帧（裁源有效）；如果不等，则是
平面与 buffer 尺寸对不上，需要改几何而不是改裁切。这一行是下一轮排查的
唯一依据，别再靠猜。

### 24.12 v7：裁切「一次失败就永久禁用」才是绿边一直在的真正原因

真机给的两张图给出了决定性证据：

```
[KMS] Esmart1-win0: ACTIVE
[KMS] format: NV12 little-endian
[KMS] dst: pos[0, 496] rect[256 x 448]
[KMS] buf[0]: pitch: 256 offset: 0
```

平面 `256x448`、pitch `256`，与 diag 页的「缓冲 256x448」**完全相等**——
平面没有比 buffer 大，绿不可能来自平面未覆盖区，只能来自**送进平面的
那一帧自己的边缘像素**。

那为什么 v5 的 6px、v6 的 16px 都没效果？看 `do_open` 的旧逻辑：

```c
g_w.use_vcrop = 1;
int built = build_pipeline(req, 0);
if (built != 0 && ... && !g_w.vcrop_failed) {
    g_w.vcrop_failed = 1;   /* ← 只要失败一次，进程内永久不再裁 */
    teardown_pipeline();
    built = build_pipeline(req, 0);
}
```

两个问题：

1. `vcrop_failed` **不随 OPEN 重置**。第一次起播只要因为任何原因（平面没就绪、
   源还没打开、甚至另一个分支的错误）建管线失败，就会被记成「裁切不可用」，
   之后**所有视频都不裁** —— 表面上看就是「改了也没用」。
2. 没有先探测 `videocrop` 是否存在。插件真的不在时，每次都要白建一次失败管线，
   既慢又掩盖了真正原因。

**v7 改法**：

- `has_videocrop()`：用 `gst_element_factory_make("videocrop")` 探测一次并
  缓存，日志打 `video: videocrop available / MISSING`；
- 每次 OPEN 重新给裁切机会，**连续失败 3 次**才彻底关；
- 带裁切且建成功 → 失败计数清零；
- `video: videoscale -> ...` 日志追加 `vcrop=16/0`，真机一眼能看出这次到底
  裁没裁。

绿边的物理来源补一条：`mppvideodec rotation=270` 走 RGA 旋转，旋转输出
可能带一圈未初始化边（YUV 0 = 绿）。这类边在**解码之后**才出现，所以必须
在解码器后面裁 —— 这正是 `videorate ! videocrop ! videoscale` 的顺序。

### 24.13 v8：不裁了，回到原生比例（定案）

用户一句话点掉了方向问题：**「为什么要裁切，直接原生比例」**。

这句话是对的。前面 v5～v7 一直在做同一件事的第七种写法：在显示链路上
剪掉画面最外圈几个像素，希望把那条绿线一起剪掉。但它治不了本：

1. **裁多少只能猜。** H.264 的 1080 按 16 宏块对齐解成 1088，多 8 行；
   部分转码稿补到 1088 或 1152，多 8~72 行。固定裁 16 对前者刚好、对后者
   不够、对小尺寸片源又砍到真画面。
2. **裁切改变的是可见区域，不是画面比例。** 绿线在源帧内容里，等比缩放
   只会把它一起缩小；把可见区域往里挪，换个片源尺寸它又从另一条边露出来
   —— 这正是"横屏消了、竖屏还在"、"左边消了、改上下"反复出现的原因。
3. **它让起播变慢。** 带裁切的管线要多一次协商；建失败还要 `teardown` 后
   去掉裁切重建一次，用户已经反馈「打开视频感觉慢了一些」。

v8 把整段裁切删干净：

| 位置 | 删除内容 |
| --- | --- |
| `session.c` 结构体 | `use_vcrop` / `vcrop_fail_count` |
| `session.c` 探测 | `g_vcrop_state` / `has_videocrop()` |
| `video_post_rate_desc` | `videocrop left/right/top/bottom=16` 拼接、`vcrop=%d` 日志 |
| `do_open` | 「建失败就去裁切重建」的整段重试 |

现在视频链路只剩一条：

```
mppvideodec(rotation=270) ! videorate ! videoscale(method=lanczos) !
video/x-raw,width=W,height=H,framerate=30/1,pixel-aspect-ratio=1/1 ! kmssink
```

- `W x H` 由 JS 的 `fitLogicalRect` 按**片源原生宽高比**算出来，等比缩放到
  可用区域里最大的内接矩形；
- `pixel-aspect-ratio=1/1` 钉死方形像素，源带非 1:1 PAR 也不会被拉伸；
- 不裁、不补边、不拉伸。

保留的两处不是裁切，别混为一谈：

- **16 网格吸附**（`alignPlane16`）：只把窗口**边界**挪到 VOP2 认的格点上。
  驱动会把 `render-rectangle` 的 x/y/w/h 一起圆整到 16，不先对齐就会多出
  几条没有 buffer 写入的扫描线（YUV 0 = 绿）。它改的是窗口位置，不动画面
  内容，比例误差 ≤3%。
- **全屏 cover 的 `cropX/cropY`**：另一个开关，默认恒为 0，第二十八轮起
  全屏已退回中列几何，不调用。

**如果绿线以后还要治，从源头查，别回到裁切：**

1. 看 `video: sink caps WxH, render-rect ...` 这行日志。caps 报的尺寸如果
   比片源真实尺寸大（1080→1088），多出来的就是解码器的宏块对齐 padding；
2. 这种情况正解是让解码器别把它当成有效内容（`crop-rectangle` / caps 里的
   真实宽高），而不是在下游剪窗口；
3. 如果 caps 与片源一致、绿线仍在，那是 RGA 旋转输出的未初始化边，属于
   驱动行为，只能接受或在解码器参数上换一条旋转路径。

守卫在 `test/run.js` 的「native: 不对源帧做固定裁切（回到原生比例）」里：
`videocrop left=16` / `has_videocrop` / `use_vcrop` / `retry WITHOUT crop`
出现任意一个就红。
